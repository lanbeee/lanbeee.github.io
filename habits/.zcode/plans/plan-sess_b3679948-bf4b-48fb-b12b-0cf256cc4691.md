# Assistant query tools: weather, schedule/availability, missed, agenda

## Principles (per your direction)
- **LLM-driven, no parser reliance** — no new regexes in `assistantGuessIntent`/`assistantPreferIntent`. The model classifies new intents and calls new query tools with structured args.
- **Answers are computed by the same primitives the UI uses** — never model-guessed: free-gap pills (`computeDayFreeGaps`), the "Could I make room?" checker (`analyzeFreeWindow`), weather sheet data (`weatherDaySummary`, `weatherPeriodSummary`, `weatherFitAssessment`).
- **Honest failure** — vague or out-of-scope queries get an explicit "I can't / unclear" reply that enumerates what the assistant CAN do.

## New surface

**Intents** (`assistant-schema.js:6`): `ask_weather`, `ask_schedule` added to `ASSISTANT_INTENTS`.
- `ask_weather`: weather lookups + "should I do X given the weather".
- `ask_schedule`: free time, freest day, will-a-block-cause-misses (what-if), what did I miss, agenda for a day/week.

**New step** `query` in `ASSISTANT_STEPS` with allowlist `['answer_weather','answer_schedule','ask_user']` (mirrors the existing classify→complete/lookup two-call pattern; keeps classify's tool schemas small). `assistantStepPredict('query')` = THINK+1024.

**Tools** (read-only, modeled on `lookup_item`; small enum-guided schemas for the local model):

- `answer_weather` — params: `query` enum `day|window|item`; `date` ("today/tomorrow/weekday/YYYY-MM-DD"); `start`,`end` (clocks "5pm"/"17:00"); `name` (existing item). Handlers:
  - `day` → `weatherDaySummary(weatherPlannerContext(settings,now), dayBase, …)` (condition, low/high, precip %, wind, city).
  - `window` → `weatherPeriodSummary(startMs,endMs,settings,null,now)`.
  - `item` → `assistantFindHabit` + find that item's placement on the day from the week timeline → `weatherFitAssessment({h,i},{placeStart,placeEnd,locId},…)` → good/caution/blocked + which rules failed; if the item has no weather rules, fall back to the window forecast for its slot.
- `answer_schedule` — params: `query` enum `free|freest|conflict|missed|day|week`; `date`; `start`,`end`; `minutes`. Handlers:
  - `free` → `computeDayFreeGaps(day,settings,now)`: total free + largest gap; with `start`/`end`: `freeWindowOverlapMinutes` check → open / what's in the way.
  - `freest` → rank all 7 week days by `computeDayFreeGaps().totalFreeMinutes` (largest gap tiebreak) → "Saturday is freest — 5h 20m free, longest block 2h".
  - `conflict` → the what-if: reuse the **UI checker core** (see refactor below) → "yes, open" / "overlaps X (fixed)" / "planner can absorb it, Y moves within the day" / "Z would spill to Saturday / off the day", plus what currently sits in that window.
  - `missed` → overdue tasks (past due, not done) + earlier-today planned rows still open (timeline + `completedToday`).
  - `day` / `week` → formatted agenda rows (clock + name) for one day or a 7-day overview (per-day planned minutes + free minutes).
  - Optional weather line appended to `free`/`conflict` windows via `weatherPeriodSummary` when forecast data exists.

Arg resolution reuses `assistantParseDue` (dates) and `assistantParseClock` (clocks); days validated to the 0–6 week horizon; durations via `assistantParseDuration`. Every handler returns `ok:true` with honest text — including "I can't answer that from your data — I can: free time, freest day, what a time block would displace, what you missed, a day/week agenda, weather, or whether weather suits an item" when args are insufficient (your vague-query requirement). No forecast → "no fresh forecast yet, open the weather panel to fetch it". Weather/schedule questions never mutate state (no `save()`).
